## Problem Statement

Most math education apps still feel like fixed courses: long explanations, linear
curricula, and generic review schedules. This hackathon app reframes lessons as
TikTok-style micro-cards: one concept, one visual, 2-3 sentences, and one practice
problem immediately after.

The product thesis: GBrain is not just storage. GBrain is the adaptive memory layer
that decides what lesson card should appear next based on what the learner has seen,
skipped, struggled with, and found engaging.

## What Makes This Cool

The demo line is:

> Duolingo has streaks. We have memory.

Every other learning app can show a curriculum. This one can explain why the next
card is right for this learner right now.

## Core User Flows

### Flow 1: First-Time Learner

1. Learner opens the app.
2. App asks what they want to learn, for example "calculus in 10 minutes."
3. App gives a 3-question diagnostic that feels conversational, not like a test.
4. GBrain writes `learner/profile.md` with current level, preferred visual style,
   and initial weak spots.
5. App generates and renders the first micro-lesson card.
6. Learner answers one practice problem.
7. GBrain records the result and queues the next card.

### Flow 2: Returning Learner

1. Learner opens the app.
2. App queries GBrain for stale concepts, weak spots, and recent engagement.
3. App says: "You got chain rule. Next is product rule. Want a review first?"
4. Learner chooses continue or review.
5. App serves the next best card, not just the next card in a static sequence.

### Flow 3: Lesson Card

1. Card appears with one animated graph, diagram, or interaction.
2. Card shows 2-3 sentences of explanation.
3. Practice problem appears on the same card.
4. Correct answer: concept confidence increases, next concept unlocks.
5. Wrong answer: misconception is logged, and a new card is generated with a
   different visual format.

### Flow 4: "What Should I Study?"

1. Learner asks what to study next.
2. App queries GBrain across learner profile, sessions, and concept memory.
3. App returns a 3-card session plan.
4. Example: "Limits are shaky, and that is blocking derivatives. Here is a
   5-minute fix."

## Long-Running Memory Model

Use Markdown for durable memory and HTML for renderable lesson artifacts. Avoid JSON
as the primary memory store because the system needs narrative state an LLM can
reason over directly.

### `learner/profile.md`

```markdown
# Learner Profile

Current goal: Understand core calculus visually.
Pace: 60-90 second cards.
Preferred visuals: animated graphs, color-coded transformations.
Avoid: long symbolic derivations before intuition.

Observed patterns:
- Drops off when cards have more than 3 sentences.
- Responds well when animation speed is controllable.
- Needs review when derivative notation changes form.
```

### `concepts/chain-rule.md`

```markdown
# Chain Rule

Status: learning
Confidence: medium-low
Last touched: 2026-05-16

What landed:
- Learner understood "outside changes after inside changes" using nested machines.

What did not land:
- Learner missed notation when `f(g(x))` became `dy/dx`.

Next best card:
- Use an animated graph with two linked sliders: inner function and outer function.
```

### `learner/sessions/2026-05-16-session-001.md`

```markdown
# Session 001

Cards shown:
- chain-rule-v1.html

Engagement:
- completed visual
- answered practice incorrectly
- spent 74 seconds

Interpretation:
- Visual was engaging, but notation bridge failed.

Memory update:
- Regenerate chain rule with less notation and stronger color mapping.
```

## Lesson Card HTML Contract

Each generated lesson should be a self-contained HTML file that the app can render
in an iframe or sandboxed preview.

Required sections:

- `concept_id`
- `lesson_id`
- visual area using inline SVG, Canvas, or D3
- 2-3 sentence explanation
- one practice problem
- answer options or input
- metadata block for GBrain ingestion

Example metadata:

```html
<script type="application/json" id="lesson-metadata">
{
  "concept_id": "chain-rule",
  "lesson_id": "chain-rule-v1",
  "visual_type": "animated-graph",
  "estimated_seconds": 75,
  "prerequisites": ["derivative", "function-composition"],
  "practice_type": "multiple-choice"
}
</script>
```

## Skill File Structure

### `skills/next-card.md`

Purpose: choose the next card.

Inputs:

- learner profile
- recent sessions
- concept memory
- due-for-review concepts
- current goal

Output:

- concept id
- reason this concept is next
- preferred visual format
- whether this is new learning or review

### `skills/generate-lesson-card.md`

Purpose: generate one self-contained HTML card.

Inputs:

- chosen concept
- learner profile
- visual preference
- previous failed cards for this concept

Output:

- HTML lesson card
- metadata block
- practice problem and expected answer

### `skills/grade-attempt.md`

Purpose: interpret the learner's answer.

Inputs:

- lesson metadata
- learner answer
- time on card
- interaction events

Output:

- correct / incorrect / partial
- likely misconception
- confidence delta
- regenerate or advance

### `skills/update-memory.md`

Purpose: write the durable memory update.

Inputs:

- grading result
- engagement signals
- prior concept file
- prior learner profile

Output:

- updated concept page
- updated session page
- next-card recommendation

## Architecture Alternatives

### Approach A: Repo-Local Static Demo

Summary: Generate lesson HTML files into the repo and render them in a simple local
web app. Store learner memory as Markdown in repo-local folders for the demo.

Effort: Small
Risk: Low

Pros:

- Fastest path to a visible hackathon demo.
- Easy for teammates to inspect, edit, and commit.
- Works even if full GBrain integration needs more time.

Cons:

- Personalization is partly simulated unless GBrain is wired in.
- Multi-user state is not real.
- The demo can look more like a prototype than a product.

Reuses:

- Git
- Markdown
- generated self-contained HTML cards

### Approach B: GBrain-First Adaptive Feed

Summary: Treat GBrain as the source of truth from the start. The app queries GBrain
for learner state, generates the next card, writes the lesson artifact back, and
updates concept memory after each attempt.

Effort: Medium
Risk: Medium

Pros:

- Best expression of the hackathon thesis.
- Demo can show real memory: "because you missed this, I changed the next visual."
- Harder to copy than a static curriculum app.

Cons:

- More moving parts during a time-boxed build.
- Requires careful prompting so memory updates stay clean.
- Debugging failures may be harder under demo pressure.

Reuses:

- GBrain search/query
- Markdown memory pages
- generated HTML lesson artifacts

### Approach C: Hybrid Demo Harness

Summary: Build a thin app that uses repo-local Markdown/HTML files as the visible
artifact layer, then calls GBrain for the "why this card next" reasoning. If GBrain
is unavailable, the demo falls back to deterministic local files.

Effort: Medium
Risk: Low-Medium

Pros:

- Shows the real product thesis without making the whole demo depend on one service.
- Team can work in parallel: UI, lesson generation, memory prompts, demo script.
- Keeps artifacts in Git for judges and teammates.

Cons:

- Requires a small adapter layer between repo files and GBrain.
- The fallback path needs to be honest in the demo.
- Slightly more planning than the pure static version.

Reuses:

- repo-local `docs/gstack/`
- Markdown memory files
- HTML lesson cards
- GBrain query/write flow

## Recommended Approach

Use Approach C: Hybrid Demo Harness.

For a hackathon, the point is not to prove that every production edge case is solved.
The point is to make the GBrain memory loop obvious and credible. The hybrid path
lets the team ship a visual demo while still showing the product moat: adaptive
lesson sequencing from long-running learner memory.

## 12-Hour Build Sequence

### Hours 0-2: Demo Skeleton

- Create the app shell.
- Render one hardcoded lesson card.
- Add the progress pulse: "you got chain rule, next is product rule."
- Create sample GBrain memory files for one learner and 3-5 concepts.

### Hours 2-4: Lesson Card Generation

- Write the prompt/skill that generates one self-contained HTML card.
- Generate cards for limits, derivatives, chain rule, and product rule.
- Keep visual formats simple: SVG graph, slider, color-coded diagram.

### Hours 4-6: Practice and Memory Update

- Add one answer interaction per card.
- Record answer outcome, time spent, and whether the learner advanced.
- Update the session memory and concept memory after each attempt.

### Hours 6-8: Adaptive Next Card

- Query memory to decide the next card.
- If wrong, regenerate the same concept with a different visual.
- If correct, advance to the next concept or schedule review.

### Hours 8-10: Demo Polish

- Make the lesson card mobile-first.
- Add 3 strong states: first-time, wrong-answer recovery, returning-user memory.
- Add a visible explanation of the memory decision.

### Hours 10-12: Script and Reliability

- Freeze demo data.
- Prepare a 90-second judge script.
- Add fallback local memory files in case live GBrain calls fail.
- Test the whole flow from blank learner to adapted next card.

## Demo Script

1. "Most learning apps remember your streak. This remembers how you learn."
2. Show first chain-rule card with one visual and one practice problem.
3. Answer incorrectly.
4. Show GBrain memory update: "notation bridge failed."
5. Show regenerated lesson with a different visual approach.
6. Answer correctly.
7. Show progress pulse: "you got chain rule, next is product rule."
8. Close: "Duolingo has streaks. We have memory."

## Success Criteria

- A teammate can open the app and complete a 3-card learning session.
- Each card is visual-first and takes less than 90 seconds.
- At least one wrong answer changes the next generated card.
- GBrain-backed memory can explain why the next card was chosen.
- The demo works with a local fallback if GBrain is unavailable.

## The Assignment

Build one complete memory loop before building more content:

`chain-rule-v1.html` -> practice answer -> session memory update -> concept memory
update -> `chain-rule-v2.html` or `product-rule-v1.html`.

If that loop is real, the product is real enough for the hackathon demo.

## What I Noticed

- You are not pitching "AI tutor" generically. You named the product moat:
  personalized long-running memory.
- The strongest phrase is "the next card is always the right card, not just the
  next card in a sequence." That should drive the whole demo.
- The HTML artifact idea is correct for a hackathon because it makes lessons
  visible, diffable, and easy for GBrain to ingest.
- The risk is overbuilding curriculum. The demo only needs one concept loop that
  visibly adapts.
